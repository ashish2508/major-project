Lag-Aware Snapshots for Replicated Key-Value Stores

Scope
A replicated key-value store must sometimes move a large snapshot while foreground requests continue. We consider followers that have fallen far enough behind for log replay to compete with ordinary traffic. The proposal targets a leader with several followers and assumes monotonically numbered log entries. It separates the question of which version to copy from the question of how fast the transfer should proceed.

Snapshot boundary
The leader seals a snapshot at a committed log index and advertises that index before sending any data. A follower stages the incoming key ranges in a separate directory. It installs the directory only after checking the manifest and the digest of every range. Log entries above the sealed index remain in a replay queue. This boundary prevents a transfer from combining keys that were observed at different points in the update history.

Transfer scheduling
A token bucket at the sender caps the amount of snapshot data emitted during each scheduling interval. Foreground reads may borrow bandwidth from an idle snapshot stream. The bucket is replenished from a rolling estimate of spare link capacity, using measurements taken before the next group of ranges is issued. A paused transfer keeps its verified ranges so that resumption begins with the earliest unchecked range.

Acknowledgment rule
The follower reports a verified range only after its contents and range identifier are durable. The leader treats this acknowledgment as progress information and never as a vote to commit an application write. When the final range arrives, the follower writes an installation marker before switching its active directory. Recovery checks the marker and the manifest together. This ordering makes a partial snapshot distinguishable from a completed installation even if a restart interrupts the switch.

Workload design
An evaluation would replay three request mixes with the same key distribution and different write fractions. Each mix would include a brief network outage followed by a controlled return to service. The design calls for separate plots of client latency and time to catch up, since a fast transfer that delays most foreground requests would fail the operational goal. No results are reported in this synthetic proposal.

Buffer pressure
A replay queue can grow while a slow follower is receiving a snapshot. The leader therefore assigns each transfer a fixed memory budget and spills excess entries into a sequential file. The follower consumes the buffered records in index order after installation. If the sender cannot retain the interval beginning immediately after the sealed index, it aborts the transfer and chooses a new boundary. This failure mode trades additional copying for an unbroken replay sequence.
